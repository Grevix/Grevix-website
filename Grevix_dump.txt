1. PRD & TRD
1.1 What is the PRD?
The Product Requirements Document defines what Grevix is supposed to achieve from a product and user perspective. It explains the problem, target users, features, scope, priorities, user stories, constraints and success criteria. It should be treated as the product agreement before implementation begins.
1.2 Project Overview
Grevix is planned as a private technology and coding community platform. The website is intended to bring together community information, member profiles, projects, events, hackathons, internships, jobs, learning resources, achievements and collaboration features in one organized system.
The current team consists of 5 developers and the community is approximately 7 members. The near-term target is 25+ members. These numbers are planning inputs and should be replaced with measured values as the platform grows.
1.3 Problem Statement
Small developer communities commonly keep information in disconnected places such as GitHub, messaging applications, spreadsheets, social media, event websites and separate job boards. This creates several practical problems: project information becomes difficult to discover, member skills are not visible in one place, opportunities are missed, event deadlines are scattered and administrators spend time maintaining duplicated information.
Grevix aims to solve this by creating a central community platform where information is structured around people, projects, opportunities and activities rather than around one generic social feed.
1.4 Product Vision
Build a practical developer-community platform that can start small with Grevix and later support a much larger community ecosystem.
1.5 Product Mission
Make it easier for developers to discover people, projects, events, opportunities and learning resources while giving community administrators a manageable system for organizing this information.

1.15 Authentication and Authorization
The proposed authentication system is Supabase Auth with GitHub OAuth. Authentication establishes identity; authorization decides what the identity is allowed to do. The planned roles are MEMBER, EDITOR, ADMIN and SUPER_ADMIN.
A member should not be able to call administrative endpoints merely by knowing their URL. Authorization must be enforced server-side and through database policies where appropriate.
1.16 Database Technical Requirements
The database should be relational and normalized. Suggested core tables are users, members, skills, member_skills, projects, project_members, technologies, events, event_categories, event_participants, opportunities, opportunity_categories, resources, blogs, achievements, teams, team_members, tasks, notifications and admin_roles.
Foreign keys should enforce relationships. Frequently filtered columns such as category, date, member_id, project_id and source should be indexed after checking actual query patterns.

2. System Architecture & Workflow
2.1 High-level Architecture
The proposed architecture separates the presentation layer, application/API layer, data services and external integrations. This prevents the UI from becoming directly responsible for sensitive credentials or third-party API complexity.

Figure 1. High-level Grevix system architecture.
2.2 Frontend Layer
The frontend contains public pages, authenticated member pages, admin pages, reusable components and client-side interaction. The frontend should not contain secret API keys. Public data can be requested through safe endpoints, while sensitive integrations should be handled on the server.
2.3 Application/API Layer
The application/API layer handles validation, authorization, database operations, external API calls, normalization, caching and AI orchestration. It acts as the control point between the user interface and services.
2.4 Data Layer
PostgreSQL stores structured community data. Supabase Auth stores/handles authentication identity and sessions. Supabase Storage can hold profile images, project images and selected documents if required.
2.5 External Integration Layer
External services may include GitHub for repositories and OAuth, Gemini for AI, Remotive and Arbeitnow for job/opportunity data, and public feeds or administrator submissions for events. Each source must be checked for current API access, terms, attribution and redistribution restrictions before production use.

2.12 Failure Workflow
External APIs can fail, change their schema, become rate limited or disappear. The application should therefore use timeouts, retries with backoff where appropriate, cached data, error states and source-specific adapters. AI failure should not break core pages that do not require AI.
3. Testing Strategy
3.1 Testing Objective
Testing is intended to verify that the application works correctly, protects user data, handles invalid input, behaves consistently across devices and fails safely when external services are unavailable.
3.2 Unit Testing
Unit tests should cover isolated functions such as validation, formatting, filtering, scoring, data normalization and utility functions. They should be fast enough to run on every pull request.
3.3 Integration Testing
Integration tests should verify boundaries between the application and Supabase, authentication, API endpoints, external data adapters and AI service wrappers.

4. UI/UX Designs and Their Inspiration
4.1 Design Direction
The intended Grevix visual direction is dark, minimal, technical, futuristic and professional. The goal is to make the site look like a serious developer community rather than a generic college club website.
4.2 Design Inspiration
The inspiration can be taken from modern developer products, GitHub-style information density, technical documentation sites, developer tooling dashboards and cinematic technology interfaces. The design should borrow principles such as strong hierarchy, clean cards, clear metadata and restrained motion rather than copying another website.
4.3 Visual Principles

Minimal decorative elements.
Strong project imagery.
Consistent cards and metadata.

7. AI Keys, APIs and Page-wise AI Integration
7.1 Important: We Do NOT Need a Different Gemini Key for Every Page
A common mistake would be creating one Gemini API key for the Hackathon page, another for the Internship page, another for the Project page and so on. That is unnecessary. One application can use one server-side Gemini credential and route different requests through different functions/prompts. If usage grows, separate credentials can be considered for isolation, quotas or operational reasons, but page separation alone is not a reason to create separate keys.
The important separation should be in software modules: /ai/hackathon, /ai/opportunity, /ai/project, /ai/learning, etc. The key stays in an environment variable and never reaches browser JavaScript.

7.5 Hackathon AI Pipeline
The hackathon page should not rely on AI to discover the original source. A source adapter should first collect data from an approved API/feed/admin input. AI can then structure or summarize the collected text. This separation makes the system more reliable and auditable.
Fetch source data.
Validate source URL and required fields.
Extract title, organizer, dates, registration deadline, location, eligibility and prize information.
Use Gemini only for ambiguous text extraction, categorization or summarization.
Validate AI output against date/type rules.
Store source URL and source name.
Display source attribution.
7.6 Internship / Job AI Pipeline
Job APIs often already provide structured fields, so AI should not be used for every request. It is more efficient to use AI only for tasks such as classification, skill extraction, summarization or recommendation.

Normalize title/company/location/type.
Deduplicate.
Store source and original URL.
Use AI for tags/summary only when useful.
Store structured fields.

7.8 GitHub API Rate-limit Strategy
GitHub documents a primary limit of 60 requests/hour for unauthenticated REST requests and generally 5,000 requests/hour for authenticated requests, while search endpoints and secondary limits have additional restrictions. The application should cache repository metadata, avoid unnecessary polling, request only required fields and handle 403/429 responses correctly. citeturn0search0turn0search6
7.9 AI Cost-Control Strategy
Do not call Gemini on every page load.
Cache generated summaries.
Generate summaries when a record is created/updated rather than every time it is viewed.
Use smaller/cheaper models for simple classification where appropriate.
Send only required text.
Limit maximum input/output size.
Use structured JSON output where supported.
Add request throttling.
Keep a fallback when AI is unavailable.
7.10 AI Safety and Accuracy
AI output is probabilistic. A generated internship summary, skill tag or hackathon classification can be wrong. Important facts such as deadlines, eligibility, prizes, company names and application URLs should come from the original source or validated structured data rather than from an AI hallucination.
For this reason, AI should enrich source data, not become the authoritative source of factual event or job information.

8.11 Recommended Final MVP
If the team has to choose between breadth and reliability, the recommended MVP is: Home + About + Projects + Community/Profiles + Authentication + Events + Opportunities + Admin Dashboard + PostgreSQL/Supabase + GitHub integration + responsive UI + basic AI summarization. Advanced team matching and real-time collaboration should wait.
This is the version most likely to be demonstrable, explainable to teachers, technically defensible and realistically finishable within the stated development window.

Conclusion
The Grevix website should be built as a modular community platform rather than a collection of unrelated pages. The PRD defines the product and the TRD defines the technical implementation. The architecture separates frontend, application logic, database services, external APIs and AI processing. Testing, security and deployment are part of the product rather than tasks to be added at the end.
The most important technical decision regarding AI is to keep AI as an enrichment layer. Gemini can summarize, classify, extract skills and generate recommendations, but source systems should remain authoritative for factual data such as event dates, application URLs, company names and deadlines. One secure server-side Gemini key can support multiple page-specific AI functions; separate keys are not required merely because the functions appear on different pages.
The final MVP should prioritize a stable community foundation. Once Grevix has real users and real data, advanced AI matching, team formation, learning paths, real-time communication and a larger developer ecosystem can be added based on actual usage rather than assumptions.
