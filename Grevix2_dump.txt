1. Project Overview
Grevix is a private technology and coding community that currently has around seven members, with the number expected to grow to twenty-five or more members in the near term. This document describes the plan for the Grevix community website, which is being built from scratch by a team of five developers over an eleven-day development window.
The website is meant to represent the Grevix community online, showcase the projects being built by members, list events and opportunities relevant to the community, and give members a shared place to collaborate. In the long run, Grevix may grow into a larger developer ecosystem that supports learning, project collaboration, opportunity discovery and AI-assisted recommendations, but the current scope is limited to establishing the core community platform.

2. Problem Statement
At present the Grevix community does not have a dedicated online presence. Member information, ongoing projects, event details and opportunities are shared informally, which makes it difficult to keep track of who is doing what, what events are coming up, and what opportunities are available to members. As the community grows past its current size, this informal approach will not scale.
There is no central place where a member can see the community's active projects, check upcoming hackathons or workshops, or find internships and job opportunities relevant to their skills. New members also have no simple way to introduce themselves, list their skills, and connect with existing projects.
2.1 Problem Impact
Community activity and member contributions are not visible or trackable.
Event and hackathon information has to be manually shared and is often missed.
Opportunities such as internships and referrals are not centrally tracked.
New members have no structured way to discover projects or find their place in the community.
There is no shared record of achievements, certifications or project history.
3. Vision and Mission
3.1 Vision
For Grevix to grow into a self-sustaining developer community where members can build real projects together, learn from one another, and discover opportunities that help them grow professionally.
3.2 Mission
To build a single platform where Grevix members can manage their profiles, showcase their projects, discover events and opportunities, and collaborate with other members. Features such as AI-based recommendations will be added later, where they can reduce manual work or make information easier to find, rather than as a starting point.
3.3 Community Values
Building real, working projects rather than only discussing ideas.
Helping other members learn and grow.
Being transparent about progress, including unfinished or in-progress work.
Encouraging participation in hackathons, competitions and open-source contribution.
4. Goals and Objectives
4.1 Goals
Give Grevix a proper public-facing website that represents the community.
Provide members with a way to manage their own profiles and projects.
Centralize information about events, hackathons and opportunities.
Lay the technical foundation for future collaboration and AI-based features.
4.2 Objectives
Launch a working version of the website within the eleven-day development period.
Support at least the core pages (Home, About, Projects, Events, Community, Opportunities, Resources, Blog, Contact) in the first release.
Implement member authentication using GitHub OAuth through Supabase Auth.
Set up a database schema that can support future features without major rework.

6. Product Scope
Given the eleven-day development window and a five-member team, the scope for the first version of Grevix is deliberately limited to the core community website and the foundational data model. Advanced features such as AI-based team formation and skill-gap analysis are documented in this report as future scope, not as part of the current build.
6.1 In Scope (Current Build)
Public pages: Home, About, Projects, Events, Community, Opportunities, Resources, Blog, Contact.
Member authentication using GitHub OAuth via Supabase Auth.
Member dashboard and basic profile management.

Manual admin submission for events and opportunities; external API integration where feasible within the timeframe.

Real-time chat or Discord-like communication features.
Mobile application.
Large-scale analytics dashboards.

9. Community Management Features
Beyond the public-facing pages, Grevix is intended to function as a community management tool for its own members. The following twelve feature areas describe the planned functionality. Not all of them will be implemented in the first eleven-day build; several are documented here as future scope so that the database and architecture can be designed to accommodate them later without major rework.
9.1 Task Assignment & To-Do Management
Supports individual and team tasks, with assignment, status, priority and deadline tracking, along with basic progress tracking for ongoing project work.
9.2 Skill Tracking & Member Profiles
Tracks each member's skills, experience, projects, achievements and learning goals, forming the data foundation described in Section 8.6.
9.3 Integrated Workflow & Collaboration
Connects project workflow and team collaboration with GitHub, including source code links and project documentation, so that project status on the site reflects real repository activity where possible.
9.4 Hackathon & Event Tracking
Covers event discovery, a shared calendar, deadline tracking, registration links, event categories and the external source pipeline described in Section 8.4.
9.5 Learning Resources
A resource library covering courses, tutorials and documentation, with learning paths and skill-based recommendations planned as a future enhancement once enough usage data exists.
9.6 Team Formation
Initially, team formation will be manual. Skill-based and role-based matching, along with balanced team suggestions, are planned as future, AI-assisted features once member profile data is populated.
9.7 Communication Hub
Centralizes announcements and team discussions. A more complete, Discord-like communication feature is listed as future scope rather than part of the current build.
9.8 Project Management Dashboard
Gives project contributors a view of project progress, deadlines, team members, task status and general project performance.
9.9 Attendance & Participation Analytics
Tracks event participation, community activity, contributions and participation trends over time, without inventing specific figures before the platform has real usage data.
9.10 Recruitment & Opportunity Board
Surfaces internships, jobs, referrals and collaboration opportunities as described in Section 8.5.
9.11 Achievement & Portfolio System
Consolidates certificates, projects, hackathon results and achievements into a portfolio view for each member, building on Section 8.7.
9.12 AI-Based Smart Features
Covers recommendations, event and opportunity summarization, skill extraction, learning recommendations, project summaries, and, in the future, team matching and skill-gap analysis. These are described in more detail in Section 24 (AI Architecture).

11. Technical Requirements Document (TRD)
While the PRD describes what the product should do, the Technical Requirements Document (TRD) describes how it will be built. It covers the architecture, technology choices, data model, APIs, security and deployment approach. The TRD is written for the development team and assumes familiarity with the functional requirements already listed in the PRD.
11.1 Technical Objectives
Build a maintainable Next.js application that can be extended by a small team.
Use Supabase for the database, authentication and storage so the team does not need to manage its own backend infrastructure.
Keep the data model normalized enough to support future features (tasks, teams, notifications) without a redesign.
Integrate external services (GitHub, event/opportunity sources, Gemini API) behind a normalization or validation layer rather than depending on any single source directly in the UI.
11.2 System Requirements
Node.js-based development environment for the Next.js application.
A Supabase project for PostgreSQL, authentication and storage.
A GitHub organization and OAuth application for authentication and repository access.
A Gemini API key for AI-related features.
A Vercel account for deployment.

14. Database Design
The database is relational and will be hosted on Supabase's managed PostgreSQL. A relational design means data is split into separate tables (for example, members, projects and skills), and relationships between them are expressed using keys rather than repeating information in every table. This keeps the data consistent and avoids duplication.

14.3 Normalization
The schema is designed to at least third normal form for the core tables: repeating groups such as a member's skills or a project's technologies are stored in separate join tables (member_skills, project_technologies) rather than as comma-separated lists in a single column. This avoids duplicate data and makes filtering and reporting easier, at the cost of requiring joins for some queries, which is a normal and acceptable trade-off for this scale of application.
14.4 Data Validation
Required fields (such as member name, project name, event date) enforced at both the application and database level.
Foreign key constraints to prevent orphaned records (e.g., an event_participant referencing a non-existent event).
Enum-style constraints or lookup tables for fields such as project status and event category.
14.5 Indexing Strategy
Primary keys are indexed by default. Additional indexes are planned on frequently filtered columns such as member_id and project_id in join tables, event date, and opportunity category, to keep list and filter queries fast as the amount of data grows.
14.6 Backup Strategy
Database backup relies on Supabase's built-in backup functionality for the plan in use. This should be confirmed against the specific Supabase plan selected for the project, since backup frequency and retention vary by plan.
14.7 Row-Level Security Considerations
Supabase supports PostgreSQL row-level security (RLS), which will be used to restrict what data a member can read or write directly from the client. For example, a member should be able to update their own profile row but not another member's, and only admin users should be able to write to tables such as events or blogs. RLS policies are considered part of the security requirements in Section 20.

Role-based access control (RBAC) means that what a user can see or do is determined by the role assigned to their account. For example, a MEMBER can edit their own profile and submit projects, an EDITOR can additionally publish blog posts, an ADMIN can manage events and opportunities, and a SUPER_ADMIN has full administrative access including managing other admin accounts. These roles will be enforced both in the application layer and through Supabase row-level security policies.
